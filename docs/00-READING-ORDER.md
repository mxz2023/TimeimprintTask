## 审核方法

每次只审核一份文档，默认整章一次审核，不再拆成多个确认点。AI先列出该章全部需要决定的规则、默认值、正常例子、异常例子、取舍与关联文档；人工可以随时要求解释、调整或提出反例。摘要辅助理解，不能替代原文，也不能漏掉不显眼的限制。

| 文档 | 人工重点核对的问题 |
| --- | --- |
| 01 业务 | 通用定义、实例、参与人、Signal和Action是否能表达已规划场景？首期24小时、3次、7天等行为是否保留正确？ |
| 02 架构 | 稳定内核边界、13个一期模块、23个未来目标模块是否合理？新增场景是否确实无需修改内核和公共表？ |
| 03 环境 | 指定版本、维护限制、数据库要求是否接受？哪些是目标，哪些必须实测？缺少环境怎样阻塞验收？ |
| 04 API | 每个操作能否表达业务需求？字段、失败响应、重复提交和分页行为是否明确？逐端点核对01。 |
| 05 数据库 | 每项业务数据存在哪里？唯一键防什么重复？历史是否保留？由懂MySQL的人复核DDL、索引和跨表约束。 |
| 06 调度 | 用“同时完成和提醒”“领取后崩溃”“暂停后恢复”等时序逐步推演；由技术审核者复核锁、事务和旧Worker行为。 |
| 07 验收 | 每项需求是否有正常与失败测试？通过标准能否客观判定？性能目标是否接受？只读测试名称不算核对断言。 |
| 08 任务 | 每一步输入、产物、依赖和验收是否明确？是否先形成真实闭环？阶段自动衔接和最终统一人工验收是否清楚？ |
| 09 路线 | 首期外范围是否准确？哪些未来场景需保留？认可候选清单不等于批准实施候选。 |
| 10 评审 | 每个原问题是否确实得到解决？是否仍有遗漏、风险或尚未验证的假设？不能只接受AI自述“已关闭”。 |
