# 01 · 通用任务平台公共业务契约

> 阅读入口与阶段状态见[00开发导航](00-READING-ORDER.md)。本文是跨场景公共业务语义和首期范围的正式来源；S01/S02专有规则见[场景契约索引](scenarios/README.md)。文档已评审不代表工程已经实现。

版本 2.2；下一份为[架构与编码约束](02-AI-CODING-GUIDE.md)。本文只定义所有场景共用的平台语义和首期交付边界；场景专有配置、状态与命令不得继续堆入本文。场景与能力规划入口见[09](09-SCENARIO-ROADMAP.md)。

## 1. 产品目标与承诺边界

TimeImprintTask 是通用任务平台，不把“任务”固定等同于定时通知。任务可以由时间、事件、条件、依赖或用户命令驱动，可以产生通知、Webhook、同步或自动执行等动作，也可以具有办理人、协作者和场景专属状态。

平台对扩展性的承诺是：已规划场景及其同类变化可以通过新增场景实现、能力实现和专有数据完成，不修改稳定内核语义和公共表。平台不承诺提前实现未知业务，也不使用万能 JSON、脚本或完整工作流引擎假装支持“任何场景”。真正出现新的跨场景稳定语义时，必须以兼容方式演进扩展契约并重新审核。

首期只交付：

| 编号 | 场景 | 交付范围 |
| --- | --- | --- |
| [S01](scenarios/S01-reminder.md) | 通用提醒 | 创建、预览、读取、修改、暂停、恢复、退役；到时生成站内通知，无需完成确认 |
| [S02](scenarios/S02-recurring-todo.md) | 周期待办 | 创建、预览、读取、修改、暂停、恢复、退役；实例可完成、跳过、稍后提醒和有限催办 |

首期产品形态固定为“本地单身份、API优先的可运行后端服务”。直接使用者是本地开发者、集成者和运维者，他们通过HTTP API创建任务、查询实例/收件和诊断执行状态；普通终端用户界面不在一期。README、完整API示例、健康检查和可诊断结果属于一期可用性的一部分，不能因为没有前端就省略。反过来，也不得把Swagger页面、管理后台或桌面界面偷加为一期交付条件。

首期运行形态是本地固定身份，不接入生产认证、组织目录或真实多租户运营体系；固定身份只能由本地接入适配器构造 ActorContext，核心业务代码不得硬编码本地用户或绕过 Policy。

首期必须完成支撑后续场景复用的稳定核心，包括通用对象与不变量、扩展注册、TransitionPlan 原子提交、场景专有数据受控物化、MySQL 公共存储、Signal/Action 运行时、幂等、审计、租约、重试、恢复和双进程竞争。团队协作、审批产品、外部事件产品、飞书/京ME/邮件、缓存、AI 和前端页面均不在首期实现范围；不实现这些未来业务，不等于可以用首期特例替代其所需的稳定扩展边界。

首期结束时，新增现有类型场景应主要增加场景代码、能力实现、专有表和装配，不修改 kernel 生产源码与公共平台 DDL。这里的“稳定”不承诺永远冻结所有接口；如果未来出现新的跨场景基础语义，只允许增加兼容契约版本并复审，不得破坏已有场景。

## 2. 通用业务对象

### 2.1 任务定义

TaskDefinition 表示可持续产生或管理任务实例的业务定义，包含稳定 definitionId、scenarioKey、scenarioConfig 及其 schemaVersion、控制状态、revision、参与人声明和触发绑定。场景配置必须先按 schemaVersion 转换成强类型对象再参与业务计算。

定义控制状态只有：

- `ACTIVE`：接受新的命令和 Signal，可生成或推进实例。
- `PAUSED`：不接受会产生新工作的输入；历史查询和场景允许的历史操作仍可执行。
- `RETIRED`：定义已退役，不再产生新实例；历史与审计保留。

定义状态不表示具体任务已经完成、审批通过或缴费成功。

### 2.2 任务实例

TaskInstance 是一次具体发生、办理或跟进。平台只解释三类生命周期：

- `WAITING`：已经创建但尚未进入办理或生效阶段。
- `ACTIVE`：当前可办理、等待外部结果或仍可能发生状态变化。
- `TERMINAL`：该实例不再接受会改变业务结果的命令。

实例同时保存不透明的 `scenarioState`。例如 S02 可以定义 PENDING、COMPLETED、SKIPPED；未来审批可以定义 WAITING_APPROVAL、APPROVED、REJECTED。平台用于通用查询的是生命周期类别，具体业务合法迁移由场景负责。

实例保存定义内容和规则的必要快照。后续修改定义不得覆盖历史实例的标题、正文、参与人、业务配置或时间语义。

### 2.3 参与主体

TaskParticipant 将人员或系统主体与任务关联，角色由稳定 roleCode 表示。平台至少允许表达所有者、办理人、协作者、审批人、关注人和通知接收人，但首期只实际使用所有者和通知接收人。

所有者、办理人和通知接收人是不同概念；接收通知不自动获得办理或完成权限。未来身份接入由 ActorContext 和 Policy 判断，不能长期信任请求体自行声明的 userId。

### 2.4 Signal 与 Action

Signal 是进入平台的持久化异步事实，来源可以是时间、外部事件、条件成立或依赖完成。人工命令是调用方同步提出的操作请求，不先转换成 Signal；两者最终复用同一个 TransitionPlan 校验和提交器。相同 providerKey + signalKey 只处理一次；乱序、重复和过期行为由平台与场景共同校验。

Action 是状态迁移产生的待执行意图，例如发送通知、调用 Webhook 或同步日历。业务状态提交与 Action Job 创建同事务完成；外部动作在事务提交后执行。渠道受理、渠道送达、用户已读和任务完成是四种不同事实。

## 3. 命令与状态迁移

用户命令或 Signal 必须经过同一条业务管道：

1. 验证调用主体、requestId、资源归属和 expectedRevision。
2. Command先取得requestId幂等锁，再按固定顺序锁定业务目标；Signal处理事务先普通读取目标标识，再按definition、trigger binding、instance、Signal的顺序加锁。两者随后重新检查定义控制状态、controlGeneration、实例生命周期和revision。
3. 调用对应场景处理器计算 TransitionPlan。
4. 平台校验终态、版本、参与人、动作和审计不变量。
5. 同事务提交状态、参与人变化、动作意图、迁移历史、审计和幂等结果。

重复的同内容 requestId 返回首次确定结果，不重复产生实例、Signal 或 Action；相同 requestId 使用不同内容返回冲突。revision 采用乐观并发控制，溢出或条件更新失败时整笔业务事务回滚。

终态命令重复提交且目标相同可以返回原结果；相反终态或终态后的非法命令必须返回冲突。不同场景可以支持不同命令，平台不能把 complete、approve、renew 等全部硬编码成统一固定流程。

Command与Signal只共享“场景决策 → TransitionPlan校验 → 原子提交”主干，不共享接收方式：Command由调用方同步提出并使用requestId幂等，Signal表示已经发生的异步事实并使用providerKey/signalKey去重。平台不得为了统一术语把Command先写成Signal，也不得让Signal绕过持久化队列直接调用命令接口。

## 4. 首期共享时间规则

S01、S02 共用 `capability-calendar` 和时间 TriggerProvider，支持：

- `ONCE`：一次性时间。
- `DAILY`：从原始基准开始每天发生。
- `WEEKLY`：按星期和本地时间发生。
- `MONTHLY`：按月份日期和本地时间发生；月份没有该日时取当月最后一天。
- `EVERY_N_DAYS`：以原始日期为锚点每 N 天发生，不按上次实际执行时间漂移。

首期固定 `Asia/Shanghai`，业务时间精确到秒。预览、创建和后台规划必须复用同一算法；边界使用 afterExclusive，不能因重复扫描生成相同 occurrenceKey 的第二个实例。

创建 ACTIVE 定义时，在同一事务内物化未来7天窗口内的WAITING实例和计划时间Signal，不提前创建Action；远期发生由后台滚动规划。时间Signal实际发生时，场景在该次Transition中创建通知和Action。一次性时间不得早于或等于创建判定时间。ONCE发生前可以改为另一个未来ONCE，发生后不能改期，也不能改成循环规则。

同步创建和滚动规划都受03规定的数量、总行数、总字节和事务时间上限约束。S01/S02首期每个定义只允许一个calendar绑定；预测会超过任一上限时，在写入前整体拒绝，不能部分创建后依赖后台补齐。未来场景需要多个触发绑定时仍可使用公共上限，但必须自行保证一次TransitionPlan不会越界。

周期规则保留原始锚点。旧实例未完成不阻塞新发生；规则修改只影响新批次和未来实例，不覆盖历史。扩展周期、工作日、农历、多时区、例外日期和结束次数属于后续能力。

## 6. 暂停、恢复、修改和退役

- PAUSED定义立即增加controlGeneration，并成为所有新规划、发生Signal处理和未开始Action副作用的父级屏障。Signal和Action保存创建时的definitionControlGeneration，Worker发现与当前定义不一致时分别IGNORED或CANCELLED。暂停后是否允许处理已有ACTIVE实例，由各[场景契约](scenarios/README.md)明确，平台不得自行推断。
- 暂停时已经领取但尚未执行副作用的工作必须在最终提交前重验；能安全退回的工作等待恢复，结果未知的外部调用保留 UNKNOWN 证据。
- 暂停时保留已提交历史；暂停区间不创建P01日历场景的新实例，所有尚未开始的既有提醒统一取消，恢复后也不补发。已有ACTIVE实例的命令边界由场景契约定义。
- 恢复再次增加controlGeneration，从当前时刻后的下一合法发生继续；新窗口使用新的代次，因此无需等待旧数据清理完成，也不会制造暂停期间的实例或通知洪峰。需要补历史的未来场景必须显式声明恢复策略。
- 修改标题、正文、参与人或场景配置时，ACTIVE/TERMINAL实例快照不变；7天窗口内尚未发生的WAITING实例在同一事务中更新快照并增加revision，时间Signal发生后按新快照生成Action。修改时间规则创建新的scheduleGeneration，同事务把旧批次未来Signal终结为IGNORED、WAITING实例迁移为TERMINAL/CANCELLED，并重建新规则7天窗口。
- RETIRED增加controlGeneration，不接受新发生，把WAITING实例迁移为TERMINAL/CANCELLED、未来Signal终结为IGNORED，并取消所有尚未开始的Action；已有ACTIVE实例是否允许结清由场景契约定义。历史实例、迁移记录、审计和已提交通知不随业务操作自动物理删除。

## 7. 可靠执行与失败语义

Action Job 使用 READY、RUNNING、RETRY_WAIT、SUCCEEDED、DEAD、CANCELLED、EXPIRED、UNKNOWN 等技术状态。Worker 通过 MySQL 租约和 executionToken 领取，处理器不得自行无限重试。

首期站内信写入本地收件箱，可以与通知投递结果在同一数据库事务提交。未来飞书、京ME、邮件等网络渠道必须在任务状态事务之外调用，并分别定义渠道幂等键、超时、可重试错误、永久错误和未知结果处理。

平台保留每次 Action Attempt。崩溃、超时或无法确认结果时不退还技术尝试次数；只有在副作用开始前被明确政策阻断的尝试可以安全退回。达到上限后进入 DEAD 并可诊断，不自动改写场景终态。

正常停机或故障停机不等同暂停。首期停机追赶策略固定为`ALL_MISSED`且不提供调用方配置：Planner恢复后不得跳过持久化cursor中的历史occurrence，而是按发生时间升序、有界批次追赶。每个遗漏occurrence的业务结果由对应场景契约定义；平台必须保留事实完整性，不能在Worker中静默丢弃。调用方需要合并历史时，应在未来以新的场景规则实现。

平台提供受控重驱：DEAD Signal以及LOCAL_TRANSACTIONAL的DEAD Action可以在权限、原因、次数和审计校验后创建关联的新记录，不能原地改回READY；EXTERNAL Action和UNKNOWN首期禁止重驱。

## 8. 扩展不变量

后续新增场景必须满足：

- 新增场景代码时，`timeimprint-task-service-kernel` 源码和公共平台 DDL 零修改。
- 场景只能访问自己的专有存储端口，不能调用公共 Mapper 或其他场景 Mapper。
- 场景处理器是确定性本地计算；相同状态和输入得到等价 TransitionPlan。
- 场景需要写专有表时，只能在 TransitionPlan 中声明强类型 ScenarioDataMutation，由注册的专有数据物化器在平台事务内写入本场景拥有的表；不得携带任意 SQL、类名或脚本。
- 场景不能直接发送通知、调用外部系统、开启事务或绕过平台审计。
- 新能力优先实现已有 Trigger、Action 或 Policy 契约；只有出现所有场景都需要的新稳定语义时才提议扩展契约。
- 新模块只在真实实现时创建，不提前生成空模块、空表或空配置。

架构验收至少用审批、外部事件和 Webhook 三个非首期样板证明扩展路径。样板只用于编译与架构测试，不等于交付完整审批、事件或 Webhook 产品。
