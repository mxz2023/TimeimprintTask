# 核心决策索引

初始平台设计的推演、问题和理由见[10技术评审](../10-TECHNICAL-REVIEW.md)。不要为了补历史形式而把既有结论重复写成多份文件。

从P02开始，只有当某项变化会修改INV-01—INV-09、kernel业务语义、公共API语义、公共表或既有稳定SPI时，才创建`ADR-NNNN-<short-name>.md`。普通场景规则、实现细节和可逆配置不创建ADR。

## ADR必须包含

- 编号、标题、状态、提出阶段和日期。
- 当前问题及真实场景证据。
- 保持现有设计的后果。
- 至少一个不改核心的替代方案及未采用原因。
- 最终决策和明确不做的内容。
- 对既有场景、INV、API、数据、迁移、兼容和运维的影响。
- 需要修改的正式契约、阶段任务和验收项。
- 回滚或升级策略。

ADR状态只允许PROPOSED、ACCEPTED、SUPERSEDED或REJECTED。只有用户明确确认后才能标ACCEPTED；ADR本身不覆盖01—08，接受决策后必须同步修改对应正式契约。被替代的ADR保持只读并链接新ADR，不删除历史理由。
