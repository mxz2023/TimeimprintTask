## 2. 已确认口径

实例标题快照为「提交周报」、描述快照为「整理本周工作」时：

| 用途 | 收件标题 | 收件正文 |
| --- | --- | --- |
| `INITIAL`（初次） | 提交周报 | 整理本周工作 |
| `CHASE`（催办） | 催办：提交周报 | 整理本周工作 |

催办前缀固定为全角「催办：」，与标题快照之间没有空格。描述为空时正文为空。`purpose`（用途）仍用 `INITIAL` 或 `CHASE`。已经生成的收件不回填。稍后提醒产生的新通知沿用被平移通知上的标题和正文。`scenarioSchemaVersion`（场景配置版本）保持 1，不新增配置字段。

正式规则在 [S02 第 4 节](../../scenarios/S02-recurring-todo.md) 和 [07](../../07-ACCEPTANCE.md) 的 S02 收件说明。本表只复述，不另立一套规则。

## 3. 锁序检查

[06 调度](../../06-SCHEDULING.md) 第 2 节的业务锁顺序是：幂等记录，然后定义、触发绑定、实例、信号、动作。同一类多行按主键从小到大锁。2026-10-01 对全部 `FOR UPDATE` 调用点核对后：

| 路径 | 当前顺序 | 结论 |
| --- | --- | --- |
| 完成、跳过、稍后提醒 | 先锁实例，再锁定义 | 与文档相反，本期要改 |
| 信号到期处理 | 定义 → 触发绑定 → 实例 → 信号 | 符合 |
| 站内通知执行、外部通知执行前 | 定义 → 实例 → 动作 | 符合 |
| 外部通知拿到结果之后 | 只锁动作 | 符合；不再回头锁定义 |
| 暂停、恢复、修改定义 | 定义 → 触发绑定，再改实例和信号 | 符合 |
| 7 天窗口规划 | 先普通读绑定，再锁定义 → 绑定 | 符合 |
| 信号和动作的领取、租约回收 | 只锁候选行 | 符合 |
| 重驱 | 只锁信号或动作根行，定义是不加锁的普通读 | 无锁序倒置，不列入本期 |

`QueueWorkers`（`timeimprint-task-service-runtime` 模块）里还有一条只锁动作就发通知的旧路径。该类没有 `@Component`，当前不会运行。本期不重新启用它。

## 4. 锁序改法

完成命令先用普通读取拿到定义编号，这个读取不作为能不能完成的依据。然后按文档锁定义，再锁实例，用锁内读到的 `revision`（版本号）做冲突判断。跳过和稍后提醒走同一个 `InstanceCommandService.execute`（`timeimprint-task-service-application` 模块），一次修改覆盖三条命令。

取消尚未发出的通知时，按 `action_job_id`（动作编号）从小到大逐行锁定后再更新。不再用一条没有排序的批量更新一次锁住多行动作。

不改公共表、HTTP 字段、kernel（稳定内核）和稳定 SPI（稳定扩展接口）。验收沿用 [A06](../../07-ACCEPTANCE.md)（完成与站内通知同时提交）：两边都先锁定义，只能形成一种先后，不会互相等待。
